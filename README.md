# СоцПоляна — админка оргкомитета

Внутренняя система для оргкомитета конференции «СоцПоляна»: комитеты и тикеты,
контент-план, заявки докладчиков, секции и расписание, генерация документов.

Репозиторий содержит **и базу, и фронтенд**: `supabase/` — схема и SQL,
`frontend/` — админка (Vite + React). Раньше схема собиралась вручную в
Supabase SQL Editor, а фронтенд жил отдельно; теперь всё лежит здесь.

## Миграции: чем это необычно

Миграции — **плоские файлы `NN_name.sql` с человеческой нумерацией**, а не
`supabase/migrations/<timestamp>_name.sql`. Так они совпадают с тем, что лежит
на GitHub, и так их удобно вставлять в Supabase SQL Editor вручную.

Следствие, о котором надо знать:

- **`supabase db reset` / `db push` их не видят** — эти команды читают только
  `supabase/migrations/`. Поэтому проверка наката делается скриптом
  `scripts/verify_schema.sh` (применяет плоские файлы через psql по порядку).
- **Автосид в `config.toml` выключен** (`[db.seed] enabled = false`) — иначе
  `supabase start` падает: сид выполняется до того, как схема создана.
  Данные вайтлиста лежат в `seed_whitelist.sql` и накатываются вручную.

### Как применить схему

**Локально (проверка, что всё накатывается с нуля):**

```bash
supabase start
./scripts/verify_schema.sh
```

**На прод** — через CLI, если эта машина залинкована с проектом
(`supabase link`):

```bash
supabase db query --linked -f supabase/28_email_templates_select_policy.sql
```

Каждый файл самодостаточен, поэтому накатываются по одному, по порядку номеров.
Перед этим имеет смысл прогнать локально `verify_schema.sh` — он собирает схему
с нуля и потому ловит то, чего в накатанной базе уже не видно.

**SQL Editor — запасной путь**, когда CLI недоступен (машина не залинкована,
чужой компьютер): скопировать файл целиком и выполнить. Так схема собиралась
изначально, руками — отсюда и плоские номера. Оба пути дают одно и то же
состояние: файлы не полагаются на инструмент, которым их накатывают.

Что **не** накатывается вместе со схемой: `seed_whitelist.sql` — это данные, а
не схема (нужен при сборке с нуля; на проде вайтлист уже есть), и
`_maintenance/reset.sql` — снос всего, отдельная ручная операция.

⚠️ **Проверять состояние прода по `supabase migration list` бесполезно.** CLI
видит только `supabase/migrations/`, а его здесь нет и создавать нельзя, поэтому
локальная колонка всегда пустая, а прод-ledger знает лишь `01`–`12` (следствие
ручной сборки). Единственный надёжный способ — спросить саму базу
(`supabase db query --linked`), например посчитать политики.

Нумерация: `NN` — порядок применения. `01`–`12` — базовые разделы,
`13`+ — доработки. Пропусков быть не должно: номер = порядок, а не версия.

## Локальная разработка

### База

```bash
supabase start          # стек: Postgres :54322, API :54321, Studio :54323
./scripts/verify_schema.sh
supabase stop
```

### Фронтенд

```bash
cd frontend
npm install
cp .env.example .env    # заполнить (см. frontend/README.md)
npm run dev
```

## Деплой

- **Фронтенд** — Vercel (`frontend/vercel.json` задаёт SPA-rewrite на
  `index.html`). Подробности и список переменных окружения — в
  [frontend/README.md](frontend/README.md).
- **Edge Function** `telegram-webhook` — обязательной командой без проверки JWT,
  т.к. Telegram не шлёт Supabase JWT:
  ```bash
  supabase functions deploy telegram-webhook --no-verify-jwt
  ```
  Инструкция по секретам и регистрации вебхука — в шапке
  `supabase/functions/telegram-webhook/index.ts`.

## Что осталось недоделанным

Что делаем дальше и в каком порядке — **[plans/ROADMAP.md](plans/ROADMAP.md)**,
по этапам MVP. Разбор технических решений и расхождений —
[docs/design/decisions.md](docs/design/decisions.md). Кратко, самое важное:

- **Разделы «Расписание» и «Документы» во фронтенде — заглушки** (этапы 4 и 5,
  они и не должны быть раньше). «Контент-план» из этого списка вышел — список и
  карточка написаны.
- **Движка авто-тикетов нет.** Правила в `auto_ticket_rules` засеяны, но
  исполнять их нечему; включатся вместе с «Секциями» (этап 4), потому что
  ссылаются на их сущности.
- **Справочник вузов не выведен в UI** — таблица `universities` есть, фронтенд
  её не читает (этап 3).
- Схема на проде и файлы миграций сведены 2026-09-18: накатаны `21`–`27`,
  передеплоен вебхук. Расхождения, которые остались, — осознанные и разобраны в
  `decisions.md`.
