## Problem Statement

Локальный репозиторий приведён в порядок: 24 плоские миграции + seed воспроизводят
схему с нуля (30 таблиц, 6 вьюх, 7 типов, 11 функций, 67 политик), `db lint` чист,
`verify_schema.sh` больше не врёт про права. Но **прод отстал от репозитория**: на нём
не накатаны миграции 23 и 24, живёт сломанная функция `check_login_token_v2`, и вебхук
задеплоен со старым кодом, который печатает `TELEGRAM_WEBHOOK_SECRET` в логи — при том
что функция вызывается кем угодно из интернета (`--no-verify-jwt`). Плюс открыт патч
`preferred_full_name`, из-за которого новые люди получают имя из Telegram латиницей.

Работа распадается на две несимметричные половины: **агент может сделать правку кода
и верификацию, но не может накатить миграции** — доступа к Supabase Dashboard у него нет.
Поэтому план строится так, чтобы вся ручная работа владельца уложилась в **один проход**.

См. Таблицу 3 (гранты), Таблицу 5 (поведенческие проверки) и Таблицу 10 (статус патчей)
в хендоффе.

## Key Findings

- **`verify_schema.sh` врал в успокаивающую сторону** — `drop schema public cascade` уничтожал `pg_default_acl`, и локальная база собиралась без единого гранта у `authenticated` → PostgREST отдавал бы `permission denied` на любой запрос, при том что накат и `db lint` проходили. Починено + добавлен ассерт. → **drives Phase 3**: если одна проверка уже врала, доверять «зелёному» прогону без перекрёстной сверки с продом нельзя.
- **Расхождения с продом разрешались в пользу прода** (арбитр — `supabase/_pulled/remote_schema_20260918.sql`, 541 строка). Четыре спорных имени колонок сняты правкой `05_applications.sql` (`course` → `education_level` + `course_number`). → **drives Phase 3**: после наката весь остаток расхождений должен уйти, и это проверяемо.
- **`applications_check` был снят на проде миграцией, которой нет в файлах.** Решение владельца: **вернуть** — правило пришло от Yandex Forms, где тезисы обязательны. → **drives Phase 2**: миграция 23, но только после диагностического SELECT — иначе `validate` упадёт на продовых строках.
- **`check_login_token_v2` — сломанный черновик**, не рабочий код: параметр `token`, тело обращается к `p_token`; пишет в колонку `status`, которой нет (есть `token_status`); возвращает `(text,text)` при объявленном `(boolean,uuid)`. → **drives Phase 2**: удалить, в файлы намеренно **не** переносить.
- **RLS не покрывает `TRUNCATE`** — только SELECT/INSERT/UPDATE/DELETE. Отсюда смысл миграции 24: у `telegram_login_tokens` политик нет вообще, значит единственная защита — отсутствие грантов. → **drives Phase 2**.
- **Две таблицы в 24 обрабатываются по-разному, и это не ошибка.** У `whitelisted_usernames` политики есть, поэтому у `authenticated` отозваны только `truncate`/`trigger`/`references` — грант и политика нужны вместе, «упрощение» до `revoke all` сломает страницу вайтлиста. → **drives Anti-Goals**.
- **Из трёх патчей `docs/wiring/` два уже применены.** Открыт ровно один — `preferred_full_name`, 2 строки в вебхуке; `grep` по `index.ts` не находит колонку, строка 136 всё ещё `.select("username")`. → **drives Phase 1**: раз передеплой всё равно нужен, патч надо положить в тот же деплой.
- **Передеплой вебхука нужен в любом случае** — дебаг с секретом убран в репозитории (`6b05ed5`), но на проде старая версия. → **drives Phase 1 + Phase 2**: одна правка кода, один деплой, оба вопроса закрыты.
- **Владелец активно мержит через веб-интерфейс GitHub** — PR #1 влит им параллельно с агентом, из-за чего пуш отбился и потребовался rebase. → **drives Phase 3**: перед пушем всегда `git fetch`.

## Anti-Goals (What NOT To Do)

- **Не ротировать секреты сейчас.** Проект на дев-тестировании, доступ к дашборду только у владельца; все секреты обновятся разом перед итоговым запуском. Это решение владельца, записано в `docs/design/decisions.md` и в память — **не переоткрывать**.
- **Не «упрощать» миграцию 24 до `revoke all` на обеих таблицах.** У `whitelisted_usernames` есть RLS-политики, и снятие `select`/`insert`/`update`/`delete` у `authenticated` сломает страницу вайтлиста.
- **Не переносить `check_login_token_v2` в файлы.** Это остаток брошенного переписывания входа, а не рабочая функция. Удаляется с прода, в репозиторий не попадает.
- **Не редактировать уже применённые к проду миграции.** Отсюда 23 и 24 отдельными файлами, а не правки в 05 и 20 (правило из `CLAUDE.md`).
- **Не воскрешать Next.js.** Попытка заброшена и лежит в `docs/archive/nextjs-frontend/` (20 файлов). Стек — Vite + React 18 + Tailwind 3 + react-router 6.
- **Не «улучшать» три заглушки по 8 строк** («Контент-план», «Секции и расписание», «Документы») — прямо запрещено в `CLAUDE.md`, пока не поставлена задача.
- **Не предлагать `supabase db push` / `db reset` как способ наката.** Миграции плоские и человеко-номерные, CLI их не видит; основной способ наката на прод — вставка в SQL Editor.

### Phase 2: Ручной прогон на проде (владелец — у агента нет доступа к Dashboard)

**Goal:** привести прод в соответствие с репозиторием: вернуть ограничение на тезисы, закрыть дыру с `TRUNCATE`, убрать мёртвую функцию, задеплоить вебхук без логирования секрета.

**Why this approach:** порядок шагов продиктован зависимостями, а не удобством. Диагностика **строго до** миграции 23, потому что `validate constraint` падает на существующих строках, а не откладывается. Миграция 24 идёт после 23, потому что 23 меняет ограничение и логично закрыть прод одним проходом. Удаление функции идёт после миграций — если что-то пойдёт не так, состояние прода легче рассуждать по шагам.

- **Шаг 0 (обязателен первым).** Выполнить в SQL Editor:
  ```sql
  select id, title, contact_email, status, created_at
  from applications
  where abstract_text is null and abstract_file_url is null
  order by created_at;
  ```
  Если строк **нет** — переходить к шагу 1. Если строки **есть** — решить по каждой (дозаполнить тезисы или оставить), и только потом накатывать 23. При падении `validate` ограничение останется `not valid`: новые заявки уже отсекаются, старые не покрыты — разобрать и перезапустить `validate constraint applications_check;`.
- **Шаг 1.** Накатить `supabase/23_return_abstract_check.sql` целиком. Миграция идемпотентна: `drop constraint if exists` → `add constraint ... not valid` → `validate constraint`, поэтому работает и на проде (ограничение отсутствует), и на чистой базе (где его уже создаёт `05_applications.sql`).
- **Шаг 2.** Накатить `supabase/24_revoke_extra_grants.sql` целиком. Не «дописывать» и не сокращать: `do $$ ... $$` блоки с `current_setting('server_version_num')::int >= 170000` нужны потому, что привилегия `MAINTAIN` появилась только в PG17.
- **Шаг 3.** `drop function if exists public.check_login_token_v2(text);`
- **Шаг 4.** `supabase functions deploy telegram-webhook --no-verify-jwt` — один деплой закрывает и убранный дебаг, и патч из Phase 1. Флаг `--no-verify-jwt` **обязателен**: Telegram не присылает JWT, и без флага вебхук перестанет принимать апдейты.
- **Шаг 5.** Секреты — **ничего не делать** (см. Anti-Goals).
- **Шаг 6.** Проверить вход в приложение end-to-end: `/login` → переход в бота → подтверждение → попадание в `/tickets`. Это закрывает вопрос «отдаёт ли вебхук 401», который в прошлой сессии был снят ручной проверкой владельца.

**Files:** только применяемые `supabase/23_return_abstract_check.sql`, `supabase/24_revoke_extra_grants.sql`. Репозиторий не меняется.
**Validates with:** после шага 1 —
`select conname, convalidated from pg_constraint where conname='applications_check'` → `validated = true`.
После шага 3 — `select proname from pg_proc where proname='check_login_token_v2'` → **0 строк**.
Эталон для шага 6 — хендофф, Таблица 5.
**Rollback:** шаг 1 — `alter table applications drop constraint applications_check;` (возврат к продовому состоянию). Шаг 2 — восстановление грантов: `grant all on telegram_login_tokens to anon, authenticated;` и `grant all on whitelisted_usernames to anon, authenticated;` (для `whitelisted_usernames` это вернёт и RLS-непокрытые привилегии, т.е. откат к «как было на проде»). Шаг 3 — восстановление не нужно: функция нерабочая. Шаг 4 — передеплой предыдущей версии функции.

**Why this approach:** в этой сессии уже был случай, когда проверка проходила зелёной и врала (см. Key Findings). Единственный способ не повторить — сверить прод с файлами заново, тем же инструментом, которым расхождения были найдены: `supabase db pull`. Сверка идёт по списку конкретных ожиданий, а не «на глаз».

## Risks & Mitigations

- **Миграция 23 упадёт на `validate constraint`.** Вероятность зависит от шага 0. Митигация: шаг 0 обязателен и стоит первым; при падении ограничение остаётся `not valid` — новые заявки уже отсекаются, старые не покрыты, прод не сломан. Разобрать строки и перезапустить `validate constraint applications_check;`.
- **Миграция 24 сломает страницу вайтлиста.** Низкая — именно ради этого у `authenticated` оставлены `select`/`insert`/`update`/`delete`. Митигация: не сокращать миграцию (Anti-Goals); при поломке — откат грантов из Phase 2.
- **Вебхук перестанет принимать апдейты после деплоя.** Средняя, и это самая неприятная из поломок: вход через Telegram — единственный способ логина. Митигация: деплоить **с** `--no-verify-jwt` (без флага JWT-проверка отсечёт Telegram); сразу после деплоя пройти вход end-to-end (шаг 6); при поломке — передеплой предыдущей версии функции.
- **Патч `preferred_full_name` изменит чьё-то имя неожиданно.** Низкая: патч применяется только при **создании нового** `people`, существующих не трогает, и при NULL в колонке ведёт себя как раньше. Митигация: не заполнять `preferred_full_name` задним числом в рамках этого плана.
- **Новый `db pull` покажет не то, что ожидается** — например, всплывут расхождения, не покрытые списком из четырёх пунктов. Средняя: снимок — дельта, и прод собирался вручную. Митигация: это **находка, а не провал** — задокументировать в `docs/design/decisions.md` и не править прод, пока владелец не решит по каждому пункту.
- **Пуш отобьётся из-за веб-мержа владельца.** Средняя — случилось в этой сессии. Митигация: `git fetch` перед пушем; при дивергенции `git pull --rebase origin main`.

## Success Criteria

- **Минимум:** прод накатан и работает — ограничение `applications_check` `validated = true`, `check_login_token_v2` отсутствует (0 строк в `pg_proc`), у `anon`/`authenticated` нет грантов на `telegram_login_tokens`, вход через Telegram проходит end-to-end, вебхук задеплоен без логирования секрета.
- **Полный:** плюс `db pull` не показывает ни одного из четырёх расхождений (в идеале — пустой), и это зафиксировано в `docs/design/decisions.md`. Плюс патч `preferred_full_name` в проде, и `grep` по `index.ts` даёт 2 совпадения вместо 0.
- **Гигиена:** `docs/wiring/` не содержит применённых патчей; ветка `consolidate-workspace` удалена (после ответа владельца); `git ls-files | grep __pycache__` пусто.
- **Не-регресс:** `./scripts/verify_schema.sh` на локальной базе по-прежнему сообщает «права ролей: OK» — то есть починка `pg_default_acl` не сломана правками этого плана.
- **Проверяемость:** каждое утверждение выше подтверждается командой с конкретным ожидаемым выводом, а не «выглядит правильно».
