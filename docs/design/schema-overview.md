# Схема БД — обзор

30 таблиц, 6 вьюх, 7 enum-типов. Разбиты на пять функциональных блоков, каждый —
пара «таблицы» + «RLS» (файлы `NN` и `NN+1`), кроме блока тикетов, где RLS лежит
в общем `02_rls_policies.sql`.

Порядок файлов в `supabase/` — это порядок применения, не версия. Ниже — что
где лежит и зачем.

## Блок 1. Комитеты и тикеты (`01`, `02`)

Основа всей модели прав: всё в системе привязано к комитету.

| Таблица | Что хранит |
|---|---|
| `people` | **Только оргкомитет** (25–30 человек). `id` = `auth.users.id`. Докладчики сюда не попадают никогда — они в `speakers` и не логинятся |
| `committees` | Комитеты. `archived_at` — комитет расформирован, но история тикетов нужна |
| `committee_memberships` | Кто в каком комитете и на каком уровне (`member` / `lead`) |
| `tickets` | Задачи. `source` = `manual` (создан человеком) или `auto` (создан правилом и закрывается только сменой линкованного поля) |
| `ticket_recipients` | Кому адресован тикет. Один recipient = «в чужой комитет», несколько = «во все» |
| `ticket_comments` | Обсуждение внутри тикета |
| `auto_ticket_rules` | Справочник правил автосоздания — конфигурация, правит только владелец |

Вьюха `ticket_actionable_by` отвечает на вопрос «кто в контексте этого тикета
имеет право действовать» — используется в UI, не в RLS.

Enum-типы: `committee_level`, `ticket_status`, `ticket_source`.

## Блок 2. Контент-план (`03`, `04`)

| Таблица | Что хранит |
|---|---|
| `content_posts` | Пост: платформа, статус, текст, дата публикации |
| `content_post_media` | Медиа, привязанное к посту |
| `content_post_revisions` | История правок. Пишется триггером `log_content_post_revision()`, а не приложением — чтобы правка через SQL Editor тоже логировалась |

Вьюха `content_posts_bank` — «банк идей»: посты, ещё не поставленные в план.

Права здесь **не по комитетам** — весь оргкомитет работает с контент-планом
на равных. Это осознанное исключение из общей модели, см. `rls-model.md`.

Enum-типы: `content_platform`, `content_status`.

## Блок 3. Заявки и секции (`05`–`08`)

Самый крупный блок: приём заявок и распределение по секциям — это два разных
этапа, разнесённых по времени (февраль и март), поэтому и файлы разные.

### Приём заявок (`05`, `06`)

| Таблица | Что хранит |
|---|---|
| `applications` | Заявка целиком: контакты, тема, тезисы, статус |
| `speakers` | Докладчики внутри заявки — разворачиваются из CSV-строки формы |
| `universities` | Справочник вузов, переиспользуется между годами |
| `application_text_revisions` | Снимки текста при доработке («на доработке» → повторная подача по email вручную) |
| `application_reads` | Отметки «прочитал(а)». Требуется минимум 2 читателя, но это не захват — читают параллельно |
| `application_comments` | Сырое обсуждение между читающими |
| `application_feedback` | Финальный текст для автора — один на заявку, редактируемое поле, не лог |
| `application_feedback_sends` | Факт отправки + `body_snapshot`, потому что `feedback.body` после отправки может быть отредактирован, а знать, что реально ушло, нужно |

Вьюха `application_read_counts` — быстрая проверка «прочитано минимум двумя».

Тезисы — текст **или** файл: `check (abstract_text is not null or
abstract_file_url is not null)`.

### Распределение по секциям (`07`, `08`)

| Таблица | Что хранит |
|---|---|
| `conference_days` | Дни конференции |
| `time_slots` | Слоты внутри дня (до обеда / после обеда), с цветом для документов |
| `sections` | Секции. Создаётся в момент первого распределения доклада в неё — отдельного экрана «создать секцию» нет |
| `section_day_numbers` | В какие дни работает секция |
| `section_slots` | Конкретный слот секции (секция × слот × аудитория) |
| `section_slot_moderators` | Модераторы слота |
| `talk_assignments` | Доклад → слот. Связь `applications` ↔ `section_slots` |
| `external_experts` | Внешние эксперты — не из оргкомитета, правят модераторы |

Вьюхи `talk_display_ids` (человекочитаемые номера докладов) и
`slot_capacity_warnings` (переполнение слота).

## Блок 4. Коммуникации и документы (`09`–`12`)

| Таблица | Что хранит |
|---|---|
| `email_templates` | Шаблоны писем с плейсхолдерами (`{full_name}` и т.п.) |
| `generated_documents` | Лог генераций: тип, ссылка на файл в Storage, кто и когда, `params` jsonb |

Вьюха `mailing_recipients` — одна строка на **заявку**, не на докладчика:
рассылка идёт одним письмом на `contact_email`, а `{full_name}` подставляет
всех соавторов через `; `. Фильтрация аудитории по статусу/секции — обычный
`WHERE` при экспорте, сохранённых сегментов в БД нет.

Генерация документов идёт **вне БД** (Node.js + Puppeteer, HTML→PDF).
В базе только цвета секций/слотов и лог. Документы строятся на live-данных,
без снимков — если участник отвалился после генерации, PDF устареет. Это
принятый риск, а не недосмотр.

Enum-тип: `generated_document_type`.

## Блок 5. Инфраструктура (`13`–`22`)

Не предметная область, а обвязка.

| Файл | Что делает |
|---|---|
| `13_storage_buckets.sql` | Три бакета: `application-files`, `content-media`, `generated-documents`. Все приватные, доступ через политики на `storage.objects` |
| `14_auth_whitelist.sql` | `whitelisted_usernames` — закрытый список, кому разрешён вход |
| `15_auth_whitelist_rls.sql` | RLS на вайтлист |
| `16_rls_fixer.sql` | Исправление дыры самоповышения до owner — см. `rls-model.md` |
| `17_telegram-deep-link-login.sql` | `telegram_login_tokens` + функции входа — см. `auth-telegram.md` |
| `18`–`22` | Точечные добавления колонок, каждая — отдельная миграция, потому что предыдущие уже накатаны |
| `23_return_abstract_check.sql` | Возврат ограничения «у заявки есть текст тезисов или файл» — было снято на проде вручную |
| `24_revoke_extra_grants.sql` | Отзыв лишних привилегий у `anon`/`authenticated` на auth-таблицах |

Про `23` и `24` стоит знать одну общую вещь: обе чинят **расхождения файлов с
продом**, а не добавляют новую функциональность. Причина каждого — в шапке
файла, разбор — в `decisions.md`.


Бакеты разделены по типу файлов, а не по одному бакету с разбором префиксов
пути: так политики проще, и правила (например, будущая очистка старья) можно
применять к бакету целиком.

## Чего в схеме нет

- **Роли «руководитель конференции»** — в контексте упоминалась, отдельной
  сущности под неё нет. Временно трактуется как `is_owner or is_any_lead`.
- **Снимков данных для генерации документов** — см. выше, осознанно.
- **Таблицы докладчиков как пользователей** — докладчики не логинятся никогда.
