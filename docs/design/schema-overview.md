# Схема БД — обзор

33 таблицы, 6 вьюх, 7 enum-типов. Разбиты на пять функциональных блоков, каждый —
пара «таблицы» + «RLS» (файлы `NN` и `NN+1`), кроме блока тикетов, где RLS лежит
в общем `02_rls_policies.sql`.

Порядок файлов в `supabase/` — это порядок применения, не версия. Ниже — что
где лежит и зачем.

## Блок 1. Комитеты и тикеты (`01`, `02`)

Основа всей модели прав: всё в системе привязано к комитету.

| Таблица | Что хранит |
|---|---|
| `people` | **Только оргкомитет** (25–30 человек). `id` = `auth.users.id`. Докладчики сюда не попадают никогда — они в `speakers` и не логинятся |
| `committees` | Комитеты. `archived_at` — комитет расформирован, но история тикетов нужна |
| `committee_memberships` | Кто в каком комитете и на каком уровне (`member` / `lead`) |
| `tickets` | Задачи. `source` = `manual` (создан человеком) или `auto` (создан правилом и закрывается только сменой линкованного поля) |
| `ticket_recipients` | Кому адресован тикет. Один recipient = «в чужой комитет», несколько = «во все» |
| `ticket_comments` | Обсуждение внутри тикета |
| `auto_ticket_rules` | Справочник правил автосоздания — конфигурация, правит только владелец |

Вьюха `ticket_actionable_by` отвечает на вопрос «кто в контексте этого тикета
имеет право действовать» — используется в UI, не в RLS.

Enum-типы: `committee_level`, `ticket_status`, `ticket_source`.

## Блок 2. Контент-план (`03`, `04`, `25`–`27`, `29`)

| Таблица | Что хранит |
|---|---|
| `content_posts` | Пост как материал целиком: **базовый текст** (один на обе площадки), статус (`idea` … `published`), дата ближайшей публикации, автор |
| `content_post_variants` | Состояние публикации **на каждую площадку** (`25`, переосмыслено в `29`): своя дата, своя ссылка на вышедший пост и **необязательное** переопределение текста. Один вариант на площадку (`unique (post_id, platform)`) |
| `content_post_media` | Карточка: текст, вшиваемый в картинку (`card_text`), и ссылка на файл. `url` может быть NULL — сначала пишется текст, картинка приходит позже |
| `content_post_revisions` | История правок **текста поста**. Пишется триггером `log_content_post_revision()`, а не приложением — чтобы правка через SQL Editor тоже логировалась |

Вьюха `content_posts_bank` — «банк идей»: посты, ещё не поставленные в план.

Почему текстов три вида, а не два. `25` развела текст по площадкам, исходя из
того, что в тг есть разметка ссылок и эмодзи-пак, а в ВК нет. Это верно, но
набрать эту разницу в нашей textarea всё равно нечем — она делается в редакторе
самой площадки при публикации. Остаётся карточка-превью (в тг встроенная ссылка
её отключает, в ВК карточка будет всегда) и подстановка эмодзи: ради этого две
полные копии текста — налог, вторая копия тихо расходится с тем, что вышло.
Поэтому `29` вернула базовый текст на `content_posts.body`, а у варианта он стал
`NULL` = «не переопределён». Текст карточки — третья сущность: он вшит в пиксели,
картинка уходит в обе соцсети одна, поэтому он один на карточку, а не на
площадку. Разбор альтернатив — в шапках `25_...` и `29_...`.

Побочный эффект `29`, ради которого она отчасти и делалась: история ревизий
снова работает. Триггер висит на `content_posts.body`, а пока тексты жили только
в вариантах, правка текста не порождала ревизию вообще — UI трогал в
`content_posts` только заголовок, статус и дату.

В `27_content_plan_revision_fix.sql` починены три латентных дефекта `03_...`,
найденных при написании раздела (`03` не правилась — она давно на проде):
пост вообще нельзя было создать (BEFORE-триггер ревизии ссылался на ещё не
вставленную строку), снимок не мог хранить отсутствующий текст, а правка вне
приложения отменялась целиком, потому что `auth.uid()` там пуст.

Права здесь **не по комитетам** — весь оргкомитет работает с контент-планом
на равных. Это осознанное исключение из общей модели, см. `rls-model.md`.

Enum-типы: `content_platform`, `content_status`.

## Блок 3. Заявки и секции (`05`–`08`, `31`, `32`)

Самый крупный блок: приём заявок и распределение по секциям — это два разных
этапа, разнесённых по времени (февраль и март), поэтому и файлы разные.

### Приём заявок (`05`, `06`)

| Таблица | Что хранит |
|---|---|
| `applications` | Заявка целиком: контакты, тема, тезисы, статус |
| `speakers` | Докладчики внутри заявки — разворачиваются из CSV-строки формы |
| `universities` | Справочник вузов, переиспользуется между годами |
| `application_text_revisions` | Снимки текста при доработке («на доработке» → повторная подача по email вручную) |
| `application_reads` | Отметки «прочитал(а)». Требуется минимум 2 читателя, но это не захват — читают параллельно |
| `application_comments` | Сырое обсуждение между читающими |
| `application_feedback` | Финальный текст для автора — один на заявку, редактируемое поле, не лог |
| `application_feedback_sends` | Факт отправки + `body_snapshot`, потому что `feedback.body` после отправки может быть отредактирован, а знать, что реально ушло, нужно |

Вьюха `application_read_counts` — быстрая проверка «прочитано минимум двумя».

Тезисы — текст **или** файл: `check (abstract_text is not null or
abstract_file_url is not null)`.

### Распределение по секциям (`07`, `08`, `31`, `32`, `33`)

| Таблица | Что хранит |
|---|---|
| `conference_days` | Дни конференции (по факту их два) |
| `time_slots` | Слоты внутри дня, с цветом для документов. **Три типа** (`kind`): докладной, пленарный, служебный. Докладных в дне три, но ограничения «ровно три» в БД нет намеренно — сетка дня может измениться |
| `plenary_items` | Пленарное событие слота: лекция, круглый стол, семинар, обсуждение. Одно на слот. Модератор — из `people` **или** из `external_experts`, ровно один |
| `plenary_participants` | Участники круглого стола (и любого формата, которому понадобятся) — внешние эксперты |
| `sections` | Секции. Заводятся кнопкой «+ секция» на доске распределения |
| `section_day_numbers` | Номер секции **в рамках дня** — сквозной через все слоты, где секция появляется. Счёт заново в каждом слоте — ошибка |
| `section_slots` | Пара (секция, слот) — то, что на доске выглядит колонкой: аудитория и модератор живут здесь |
| `section_slot_moderators` | Модератор пары. Строго один: первичный ключ и есть внешний |
| `talk_assignments` | Доклад → пара (секция, слот), с номером внутри пары. Связь `applications` ↔ `section_slots` |
| `external_experts` | Внешние эксперты — не из оргкомитета, правят модераторы |

**Слот бывает трёх типов, и это свойство самого слота, а не того, что в нём
лежит.** `talk` — параллельные секции с докладами, то, что распределяется на
доске. `plenary` — одно событие: лекция, круглый стол, семинар, обсуждение; у
него есть модератор, а у круглого стола ещё и участники. `service` — регистрация,
кофебрейк, открытие и закрытие: содержания нет вообще, только подпись слота.
День на доске читается одним списком слотов разных типов, поэтому кофебрейк
между докладами не пропадает из виду.

Инвариант «лекция бывает только в пленарном слоте» держит **внешний ключ**, а не
UI: у `plenary_items` есть генерируемая колонка-константа `slot_kind =
'plenary'`, и составной ключ `(slot_id, slot_kind)` ссылается на
`time_slots(id, kind)`. Обратная сторона — тип слота нельзя сменить, пока в нём
стоит элемент. Разбор и отброшенные альтернативы — в шапке `33` и в
`decisions.md`.

**Секции идут параллельно** — это главное, чего не предполагала исходная схема.
В одном слоте одновременно работает несколько секций в разных аудиториях:
А, Б, В занимают все три слота первого дня, Г — только второй слот, Д, Е, Ж —
весь второй день. Отсюда две правки, обе видны только на живых данных:

- **Вместимость считается на пару (секция, слот), а не на слот.** 4–6 докладов —
  это про одну аудиторию; суммировать по слоту значит кричать «переполнение» там,
  где в каждой из трёх параллельных секций по пять докладов. Группировка
  `slot_capacity_warnings` переехала на `section_slot_id`, порог `> 6` не менялся —
  это контракт вьюхи;
- **`talk_display_ids` соединялась с `section_day_numbers` внутренним join**, и
  доклад в секции, которой номер в этом дне ещё не проставлен, **молча исчезал из
  вьюхи**. Теперь `left join`: пропуск стал видимым (`display_id is null`), а не
  тихим отсутствием строки.

`31` пересоздаёт обе вьюхи, `32` добавляет `reorder_talks` — RPC, которой
фронтенд переставляет доклады в ячейке целиком. Набором отдельных `update` это
не собирается: номер уникален внутри пары, проверка идёт построчно, а каждый
запрос PostgREST — своя транзакция (разбор в `decisions.md`).

`33` добавляет типы слотов и пленарную часть. Обе вьюхи выше её не замечают и
замечать не должны: и `talk_display_ids`, и `slot_capacity_warnings` ходят в
докладную часть через `section_slots`, а у пленарного и служебного слота строк
там нет вообще. Пленарный слот не попадает в предупреждение о вместимости не
потому, что это обработано, а потому, что ему нечего туда принести.

Права на новые таблицы — комитет «Модераторы/лекции/круглые столы», тот же, что
уже правит `external_experts`. Тип слота правит «Расписание секций»: `kind` —
колонка `time_slots`, а политика там на таблицу, не на список колонок. Следствие
видно в UI: слот заводит один комитет, а лекцию в нём заполняет другой.

**ID доклада склеен из четырёх однозначных компонентов** (`день-слот-секция-номер`,
1111), поэтому при 10 и более секциях в дне или 10 и более докладах в паре номера
начинают совпадать. Ограничения в БД нет намеренно — жёсткий предел мешал бы в
день конференции; вместо него баннер в UI и запрос-ловушка
`supabase/sql-checks/find_display_id_collisions.sql`.

## Блок 4. Коммуникации и документы (`09`–`12`)

| Таблица | Что хранит |
|---|---|
| `email_templates` | Шаблоны писем с плейсхолдерами (`{full_name}` и т.п.) |
| `generated_documents` | Лог генераций: тип, ссылка на файл в Storage, кто и когда, `params` jsonb |

Вьюха `mailing_recipients` — одна строка на **заявку**, не на докладчика:
рассылка идёт одним письмом на `contact_email`, а `{full_name}` подставляет
всех соавторов через `; `. Фильтрация аудитории по статусу/секции — обычный
`WHERE` при экспорте, сохранённых сегментов в БД нет.

Генерация документов идёт **вне БД** (Node.js + Puppeteer, HTML→PDF).
В базе только цвета секций/слотов и лог. Документы строятся на live-данных,
без снимков — если участник отвалился после генерации, PDF устареет. Это
принятый риск, а не недосмотр.

Enum-тип: `generated_document_type`.

## Блок 5. Инфраструктура (`13`–`22`)

Не предметная область, а обвязка.

| Файл | Что делает |
|---|---|
| `13_storage_buckets.sql` | Три бакета: `application-files`, `content-media`, `generated-documents`. Все приватные, доступ через политики на `storage.objects` |
| `14_auth_whitelist.sql` | `whitelisted_usernames` — закрытый список, кому разрешён вход |
| `15_auth_whitelist_rls.sql` | RLS на вайтлист |
| `16_rls_fixer.sql` | Исправление дыры самоповышения до owner — см. `rls-model.md` |
| `17_telegram-deep-link-login.sql` | `telegram_login_tokens` + функции входа — см. `auth-telegram.md` |
| `18`–`22` | Точечные добавления колонок, каждая — отдельная миграция, потому что предыдущие уже накатаны |
| `23_return_abstract_check.sql` | Возврат ограничения «у заявки есть текст тезисов или файл» — было снято на проде вручную |
| `24_revoke_extra_grants.sql` | Отзыв лишних привилегий у `anon`/`authenticated` на auth-таблицах |

Про `23` и `24` стоит знать одну общую вещь: обе чинят **расхождения файлов с
продом**, а не добавляют новую функциональность. Причина каждого — в шапке
файла, разбор — в `decisions.md`.


Бакеты разделены по типу файлов, а не по одному бакету с разбором префиксов
пути: так политики проще, и правила (например, будущая очистка старья) можно
применять к бакету целиком.

## Вьюхи: `security_invoker` (`30`)

Не блок, а поправка ко всем шести вьюхам сразу — поэтому отдельно.

Вьюха в Postgres 15+ выполняется **с правами владельца**, а не спрашивающего, и
значит идёт мимо RLS базовых таблиц. Владелец здесь `postgres`, а Supabase своими
дефолтными привилегиями выдаёт `anon` `select` на каждую новую таблицу — и `alter
default privileges … on tables` покрывает вьюхи тоже. Итог: `anon`-ключ лежит в
бандле фронтенда и публичен по определению, а через вьюхи наружу уходило то, что
табличными политиками закрыто. Хуже всего `mailing_recipients` — контактные email
всех заявителей и тексты фидбека.

`30` ставит всем шести `security_invoker = true`: вьюха начинает работать с
правами того, кто её спрашивает, и табличные политики снова действуют. Для
вошедшего оргкомитета не меняется ничего — на всех базовых таблицах есть политика
`select` «весь оргкомитет».

⚠️ Поэтому в `31` обе вьюхи создаются `create view … with (security_invoker =
true)`, а не `alter view` после: пересоздание вьюхи настройку сбрасывает, и
`create or replace` тут не годится — у `slot_capacity_warnings` меняется состав
колонок, а Postgres запрещает переименовывать их через `or replace`.

## Чего в схеме нет

- **Роли «руководитель конференции»** — в контексте упоминалась, отдельной
  сущности под неё нет. Временно трактуется как `is_owner or is_any_lead`.
- **Снимков данных для генерации документов** — см. выше, осознанно.
- **Таблицы докладчиков как пользователей** — докладчики не логинятся никогда.
