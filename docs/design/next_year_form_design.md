# Форма заявки на конференцию — дизайн полей (Yandex Forms)

Три структурных изменения относительно старой формы:
1. **Нет делимитеров** — вместо одного поля "ФИО через запятую" на всех
   соавторов — общий блок (контакты/формат/секция) + отдельный блок на
   каждого автора. Запятые внутри значений (напр. "НИУ ВШЭ, Москва")
   перестают быть проблемой в принципе.
2. **"Одинаковые для всех?" — сокращение для частого случая**, когда все
   соавторы из одного вуза/курса/города — не заставляем вписывать
   одно и то же N раз.
3. **Слепое рецензирование** — заложено на уровне UI админки (не формы), но
   определяет, что чтение/скоринг заявки не показывает ФИО/вуз/контакты, пока
   не отправлен email с решением. Раздел про это — в конце документа.

Ограничение Yandex/Google Forms: нет динамических повторяющихся блоков.
Поэтому — фиксированное число блоков "Автор N" (см. вопрос про количество).

---

## ОБЩИЙ БЛОК (один на заявку)

### 1. Формат участия
**Тип:** Один из списка (radio)
**Варианты:** Доклад / Организация секции (свои докладчики, от 3 тезисов) /
Модератор без доклада / Другое (уточнить)

### 2. Тема доклада
**Тип:** Короткий текст — «Тема вашего доклада (рабочее название)»

### 3. Желаемая секция
**Тип:** Один из списка с вариантом "свой вариант"
**Варианты (6-7 примерных тем + служебные):**
- [Тема 1] / ... / [Тема 6]
- Пока не знаю / нет предпочтения
- Свой вариант (текстовое поле)

### 4. Email для связи
**Тип:** Короткий текст с валидацией email

### 5. Телефон (необязательно)
### 6. Соцсети (необязательно)

### 7. Тезисы: текст ИЛИ ссылка на файл
**7a:** Длинный текст, необязательное — «Текст тезисов (500-700 слов)»
**7b:** Короткий текст, необязательное — «Ссылка на файл с тезисами (Google
Drive, доступ "Все, у кого есть ссылка" → "Читатель")»
Инструкция жирным: «Заполните хотя бы одно из двух полей выше».

### 8. Соавторы — все из одного вуза/курса/города? **[НОВОЕ]**
**Тип:** Один из списка (radio)
**Вопрос:** «Все соавторы учатся в одном вузе, на одном курсе и в одном
городе?»
**Варианты:** Да / Нет (или заявка на одного автора)

Определяет, какой блок появится дальше (условная логика Yandex Forms —
Yandex Forms поддерживает показ вопросов по условию ответа на предыдущий).

### 9. Общие вуз/курс/город **[показывается только если в п.8 выбрано "Да"]**
- Вуз — короткий текст
- Курс — короткий текст («3», «магистратура 1» и т.п.)
- Город — короткий текст

---

## БЛОК "АВТОР N" (повторяется; поля вуз/курс/город внутри блока
## показываются только если в п.8 выбрано "Нет")

Автор 1 — обязателен. Автор 2+ — весь блок необязателен.

- **ФИО** — короткий текст
- **Курс** — короткий текст (скрыто, если п.8 = "Да")
- **Вуз** — короткий текст (скрыто, если п.8 = "Да")
- **Город** — короткий текст (скрыто, если п.8 = "Да")

## Импорт: `import_applications.py`

Логика переписывается под новую структуру, когда форма будет готова и
известны точные заголовки колонок:
- Если п.8 = "Да" — общие вуз/курс/город применяются ко всем непустым
  блокам "Автор N" (по ФИО).
- Если "Нет" — читаем поля из каждого блока напрямую, без делимитеров.
- Пустое ФИО в блоке "Автор N" — этот автор просто пропускается, это
  ожидаемо для заявок с одним автором, не требует флага ручной проверки.
- Новое поле `city` — читается либо из общего блока (п.9), либо из блока
  автора, пишется в `speakers.city` (миграция `20_speakers_city.sql`).

## Слепое рецензирование (админка, не форма)

**Что скрыто при чтении/скоринге заявки** (до отправки решения автору):
`speakers.full_name`, `speakers.university_raw`/`city`, `applications.contact_email`,
`contact_phone`, `contact_social`. Курс — по умолчанию тоже скрыт (редко
идентифицирует сам по себе, но может в сочетании с темой в маленьком
сообществе; можно ослабить, если мешает).

**Что видно всегда:** `title`, `proposed_topic`, `desired_section`,
`participation_format`, текст/файл тезисов, статус.

**Момент раскрытия:** не при смене статуса (accepted/rejected can flip
during deliberation) — раскрывается только после факта отправки email с
решением, т.е. по записи в `application_feedback_sends` (уже существующая
таблица — это неизменяемый лог отправки, ровно то событие, которое нужно
как триггер).

**Уровень защиты:** UI-level, не DB-level (RLS остаётся как есть — все
данные технически читаемы через прямой запрос членом оргкомитета, просто
интерфейс их не показывает на экране чтения/скоринга до раскрытия). Это
сознательное решение — доверенный маленький оргкомитет, не нужен
DB-enforced blind review.

**Что нужно в коде `ApplicationDetail` (уже существующий компонент):**
- Проверка: есть ли строка в `application_feedback_sends` для этой заявки.
- Если нет — рендерить блок докладчиков без ФИО/вуза/города (напр.
  «Автор 1», «Автор 2» вместо реальных имён), контакты — скрыты полностью.
- Если есть — показывать как сейчас, полностью.

Реализовать в коде, когда форма и импорт будут готовы (или раньше, отдельно
от формы — это чисто изменение админки, не зависит от новой формы).
