# Модель прав (RLS)

## Основа: права привязаны к комитету, не к роли

Глобальных ролей в системе нет — есть **членство в комитете** с уровнем
`member` / `lead` и один флаг `people.is_owner` (владелец системы, он же —
создатель комитетов).

Вспомогательные функции (`02_rls_policies.sql`) — все `security definer`,
чтобы проверка внутри политики не упиралась в RLS той же таблицы:

| Функция | Отвечает на вопрос |
|---|---|
| `is_owner(person)` | Это владелец системы? |
| `is_any_lead(person)` | Лид **хоть какого-нибудь** комитета? |
| `is_committee_lead(person, committee)` | Лид **этого** комитета? |
| `is_committee_member(person, committee)` | Состоит в этом комитете (любой уровень)? |
| `is_selection_committee_lead(person)` | Лид комитета «Отбор заявок» (по имени) |
| `is_schedule_committee_member(person)` | Участник комитета «Расписание секций» |
| `is_moderators_committee_member(person)` | Участник комитета «Модераторы/лекции/круглые столы» |

Последние три определяют комитет **по имени строкой**. Это хрупко: переименование
комитета в UI молча ломает права. Осознанный компромисс MVP — если появится
экран переименования комитетов, эти функции надо переводить на флаг в
`committees`.

`people` — это **только оргкомитет**. Поэтому «весь оргкомитет» выражается как
`exists (select 1 from people where id = auth.uid())`. Докладчики в `speakers`
и никогда не логинятся, их email — только для рассылок.

## Три уровня доступа

| Уровень | Как выражается | Где |
|---|---|---|
| **Весь оргкомитет** | `exists (select 1 from people where id = auth.uid())` | Контент-план, заявки, коммуникации, документы, Storage |
| **По комитету** | `is_committee_member` / `is_committee_lead` | Тикеты, членство, расписание |
| **Только владелец** | `is_owner(auth.uid())` | Структура (комитеты, правила автотикетов), вайтлист, `people.is_owner` |

### Тикеты — единственное место со сложной логикой

Чтение тикетов открыто всем аутентифицированным. «По умолчанию видны только
тикеты своих комитетов» — это **UI-фильтр, а не ограничение доступа**: смысл в
том, что можно «зайти помочь в чужой тикет», поэтому на уровне БД запрещать
нечего.

Создание:
- внутри своего комитета — любой участник;
- в чужой комитет, один recipient — любой участник origin-комитета;
- несколько/все комитеты — owner или любой lead.

Обновление разрешено только для `source = 'manual'`. **Для `auto`-тикетов
update-политики нет намеренно** — они закрываются сменой линкованного поля
объекта через серверный процесс с service role, минуя RLS.

Проверка «ровно один recipient для не-lead» на уровне БД — мягкая: полный
контроль через RLS на INSERT без дополнительного состояния громоздок и
дублировал бы app-валидацию, которая всё равно нужна для UX.

## Ловушка: permissive-политики комбинируются через OR

**Это самая важная часть документа.** В `16_rls_fixer.sql` исправлена реальная
дыра, и тот же паттерн легко воспроизвести снова.

Postgres объединяет несколько permissive-политик на одну команду через OR —
**отдельно для `USING` и отдельно для `WITH CHECK`**, а не парами «своя политика
целиком». В паре `people_update_self` / `people_update_owner` это давало:

```
USING:      (id = auth.uid())          OR  is_owner(auth.uid())
WITH CHECK: (is_owner не менялся)      OR  true          ← вот проблема
```

Второй `WITH CHECK` был безусловным `true`. Значит, любой пользователь,
обновляющий **свою же** строку (проходит `USING` первой политики),
автоматически проходил общий `WITH CHECK` благодаря `true` из второй — и мог
выставить себе `is_owner = true` в обход защиты `people_update_self`.

**Правило на будущее:** политика с `with check (true)` допустима только тогда,
когда её `using` действительно ограничивает круг лиц до безопасного. Если
рядом есть вторая политика на ту же команду — общий `WITH CHECK` становится
объединением, и `true` в любой из них открывает всё.

Исправлено: `people_update_owner` теперь имеет `with check (is_owner(auth.uid()))`
вместо `true`.

## Вторая ловушка: `for all` и `with check` на UPDATE

`16_rls_fixer.sql` чинит и это. Политика `email_templates_write_org` была одна
на все команды (`for all`) с условием `with check (created_by = auth.uid())`.
Для UPDATE это значит: если правит не автор, new-версия строки всё равно
содержит старый `created_by` (при редактировании текста его не трогают) —
и `with check` проваливается. На практике шаблон мог редактировать только его
создатель, что противоречило намерению «пишет весь оргкомитет».

Исправлено разделением на `insert` / `update` / `delete`: `created_by = auth.uid()`
обязателен только при создании, при редактировании проверяется лишь членство
в оргкомитете.

**Правило:** не используй `for all` там, где условия insert и update разные.

## Инфраструктурные таблицы

- **`whitelisted_usernames`** — читает весь оргкомитет, пишет только владелец.
- **`telegram_login_tokens`** — **ни одной политики, намеренно.** Единственный
  доступ — через `security definer` функции и service role вебхука. Контроль
  доступа здесь в том, что нужно знать точное значение `token` (24 случайных
  байта), а функции его не перечисляют. Подробности — `auth-telegram.md`.
- **`storage.objects`** — бакеты приватные (`public = false`), доступ через
  политики. `public = true` открыл бы файлы вообще всем в интернете без
  авторизации, поэтому он не используется, хотя файлы «открыты всему
  оргкомитету».
- **`generated_documents` и бакет `generated-documents`** — нет delete-политики:
  история генераций неизменяема.
