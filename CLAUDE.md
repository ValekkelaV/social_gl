# Работа над «СоцПоляной» — соглашения проекта

Проект вёл Claude Web, потом код переносили в этот репозиторий вручную. Этот
файл фиксирует, как здесь принято писать, чтобы новые правки не выбивались из
уже существующего стиля.

## Язык

**Комментарии, документация, сообщения об ошибках — по-русски.** Английский
только в коде (идентификаторы, SQL, JS/TS) и в именах файлов. Так писался весь
существующий SQL — не переключайся на английский без просьбы.

## SQL: комментарии — это половина работы

Файлы миграций намеренно плотно закомментированы, и это не перебор, а стиль —
самый крупный файл (`02_rls_policies.sql`) на треть состоит из объяснений.
Правила:

- **Заголовок в шапке файла** — рамкой из `-- ===`, с названием и абзацем
  «почему так». Не «что делает» (это видно из кода), а **почему выбран такой
  вариант** и какие альтернативы отброшены.
- **Поясняй ловушки Postgres/RLS, а не синтаксис.** Образец —
  `16_rls_fixer.sql`: там на 20 строк кода ~25 строк объяснения, почему
  комбинирование permissive-политик через OR открывало дыру самоповышения до
  owner. Вот такие вещи и надо писать.
- **Inline-комментарии** — для неочевидных полей: единицы измерения, форматы
  («текст, не int: встречаются неоднородные форматы»), опциональность.
- **`comment on column/table`** — для всего, что попадёт в интерфейс или будет
  читаться не-программистом: почему NULL допустим, что значит значение.

## Миграции

- Файлы плоские: `supabase/NN_name.sql`. **Не создавай `supabase/migrations/`** —
  этот путь занят другой конвенцией и конфликтует с текущей (см. README).
- Номер = порядок применения, сквозной, без пропусков.
- **Уже применённую к проду миграцию не редактируют** — только новая. Поэтому
  `personal_email` лежит в `22_*.sql`, а не дописан в `20_*.sql`.
- Каждая миграция самодостаточна: открывается `-- ===`-шапкой, объясняющей
  контекст, и не полагается на комментарии из середины другой миграции.
- Если миграция что-то добавляет по итогам переписки — так и напиши («см. чат»,
  «по итогам ревью 02 и 10»), как в `16_rls_fixer.sql`.
- `_maintenance/reset.sql` — **не миграция**. Не включай его ни в какой накат.

## RLS

- Модель — **права по комитетам, не глобальные роли**. Помощники: `is_owner`,
  `is_committee_lead`, `is_any_lead`, `is_committee_member` (определены в
  `02_rls_policies.sql`). Прежде чем писать новую политику — посмотри, есть ли
  подходящий помощник.
- Осторожно с несколькими `for all` / permissive-политиками на одну команду:
  Postgres склеивает их через OR **отдельно для USING и отдельно для WITH
  CHECK**. Безусловный `with check (true)` в одной политике открывает дыру в
  другой. Разбор — в `16_rls_fixer.sql`.
- «Весь оргкомитет» = `exists (select 1 from people where id = auth.uid())`.
  `people` — это только оргкомитет; докладчики в `speakers` и **никогда не
  логинятся**.

## Python-скрипты

- `scripts/import_applications.py` — прошлый сезон (**Google Forms**, с
  разделителями-запятыми внутри полей).
- `scripts/import_applications_v2.py` — текущий сезон (**Yandex Forms**, без
  делимитеров вообще). Это не «версия 2 того же», а другой формат формы.
- Оба генерируют **SQL-файл с INSERT-ами**, а не пишут в БД напрямую — доступ к
  базе не предполагается. Не добавляй в них прямые подключения к Supabase.
- Комментарии и docstring — по-русски, с разбором «почему такая логика разбора»,
  как в шапке `import_applications.py`.

## Фронтенд

- Vite + React 18 + Tailwind 3 + react-router 6. **Не Next.js** — более ранняя
  попытка на Next.js заброшена (`docs/archive/nextjs-frontend/`), не воскрешай.
- Страницы — `frontend/src/pages/*.jsx`, роуты — в `App.jsx`, навигация — в
  `layout/NavShell.jsx`.
- Дизайна нет намеренно: только структура и функциональность, базовые классы
  Tailwind без брендинга.
- Разделы, которые ещё не сделаны, — заглушки на 8 строк. Не «улучшай» их
  заранее.

## Правки из чата

Инструкции вида «заменить строку X на Y», написанные в чате, — это **не
документы, а патчи**: применяй их к коду, а не переноси текст в README.

Под такие патчи заведён `docs/wiring/`; сейчас его нет — все три лежат в
`docs/archive/wiring/`, потому что применены. Правило: **неприменённый патч —
открытая задача, применённый — история**. Применённый уходит в архив, а не
остаётся рядом с кодом, иначе следующий читатель применит его второй раз.
